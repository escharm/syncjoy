# 通道队列无界，持有 PeerLink 不消费会积压

## 后果

`PeerLink` 的收包队列是无界通道。来向消息持续累积而消费追不上时，宿主表现为内存持续上涨，且没有背压反馈，发送方无从感知。

## 待区分的两个场景

- **场景 A：宿主从不消费**（`recv` 与 `on_msg` 都没调用、事件循环没跑）：更像宿主代码写错（忘了消费或忘了关闭），期望的正确行为可能是尽早、显式地暴露错误（比如消费侧缺位时直接报错或断连），而不是靠容量兜底；
- **场景 B：宿主在消费但慢于对端发送**：真实的背压需求，需要容量上限与满时的拒绝策略。

## 场景 B 的细分清单

瞬时落后（缓冲是正确行为，队列吸收抖动，容量只要够大就不丢不错）：

1. 移动端切后台或进程被冻结：恢复后一次性面对窗口期积压；
2. GC 停顿、UI 渲染卡顿、CPU 被其他任务抢占：消费停滞几十到几百毫秒，对端以正常速率发送；
3. 单条大消息解析贵（应用载荷自定义，如整段状态同步）：串行回调语义下后续消息排队等它。

持续性落后（缓冲是错误行为，内存无界上涨，必须显式失败）：

4. 回调里有慢 I/O 且不知道回调是串行的（每条都写盘、调外部 API、等锁），处理速率低于到达速率，最常见的宿主错误形态；
5. 同步协作高频操作叠加贵处理（大文档上每次按键触发全量重算）；
6. 全局瓶颈：多条连接的回调共享同一个慢管道，总消费速率低于总生产速率，单连接看是慢，根因在全局；
7. 对端失控或恶意（代码死循环重发、故意以线速灌包）：本端消费正常也追不上，有界队列在此保护宿主进程，这是安全面。

## 现状

- 队列是唯一投递路径，`on_msg` 是它的回调视图；
- `Event::Channel` 事件队列同为无界，不消费事件的宿主会积压来向连接事件；
- 末位 `PeerLink` 被 drop 会回收整条连接（队列随之消失），积压只发生在「持有句柄但不消费」的窗口内。

## open questions

1. 场景 A 与 B 如何在 SDK 内区分（或只能靠文档约定）；
2. 队列上限取多大：要覆盖瞬时落后 1-3 的量级（移动端后台窗口、GC 停顿）而不过早误伤；
3. 满时的拒绝策略：倾向断连并携带明确原因（持续落后 4-7 的正确暴露），对端 `send` 收到失败后自行决定重发或放弃。
