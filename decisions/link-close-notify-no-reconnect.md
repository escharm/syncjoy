# 断链只通知原因，不内建自动重连

## 结论

连接层不内建任何自动重连。信令断链时 SDK 发 `RelayClosed { reason }`，`reason` 携带死因（socket 被关闭、坏帧、发送失败）；是否重连、何时重连、以什么节奏重连（退避、上限、放弃）全部归宿主，重连就是宿主重新调用 `connect_relay`。边界对齐低层 WebSocket：`onclose` 携带 code/reason，重连策略是应用层的事。

## 理由

- 重连时机与宿主业务状态耦合：宿主可能需要先落盘、先结束事务、或先提示用户，SDK 无法替宿主选；单方面重连会让宿主在不知情的情况下回到在线，造成状态错位；
- 原因是重连决策的输入：socket 被对端关闭（重连大概率成功）、坏帧（协议异常，重连大概率复发）、发送失败（本地网络问题，重连无意义），宿主对不同死因应有不同策略，所以事件必须带原因而不是一个裸信号；
- 数据面同构处理：DataChannel 关闭同样只通知（`on_close`），既有直连不因信令断链被拆除，重拨与否归宿主。

## 否决过的方案

- SDK 内建指数退避自动重连：被否决。状态协调问题不因加了退避而消失，只是把错位推迟到重连成功那一刻；
- builder 开关的 opt-in 自动重连：被否决。两套路径两套语义，且 opt-in 同样绕不开「宿主不知情地回到在线」，等于把同一个问题做两遍。
